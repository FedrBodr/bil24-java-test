# BIL24 Java: спецификация выполнения

Дата: 2026-09-15. Статус: **одобрена владельцем 16.09.2026; реализация и измерения выполнены, идёт финальное ревью**.

## 1. Цель и границы

Подготовить два проверяемых решения тестовых заданий BIL24 и показать эффект оптимизаций на воспроизводимых измерениях. Первая задача требует совместимости с оригинальным Java-кодом. Вторая требует объяснения алгоритма; в наш объём дополнительно включён небольшой работающий пример с тестами и измерениями.

Результат — самостоятельный публичный GitHub-репозиторий. Веб-сервер, база данных, UI и деплой для этих задач не требуются. Подготовка решения не подразумевает отправку сообщений представителям BIL24.

## 2. Общие ограничения

Эти строки должны присутствовать без изменений в обоих планах:

- Java: исходный и целевой уровень 17; проверки на JDK 17 и 21; измерения на JDK 21.
- Сборка: Maven 3.9.9 через Maven Wrapper; версии зависимостей и плагинов фиксированы.
- Зависимости: основной код — только Java Standard Library; JUnit Jupiter 5.11.4 — тесты; JMH 1.37 — модуль benchmarks.
- Оформление: UTF-8, два пробела, K&R, без табуляций в Java-коде, осмысленные английские имена.
- Документация: русский язык, точные команды, фактические результаты и явно обозначенные ограничения.
- Эталон: SHA-256 архива 53be3446279e6312167e100cd86c66525801fcde78d3fac918f3ec1ed591a1b2; исходники эталона и бинарные сборки с ним не публикуются в Git.
- Процесс: реализация после ревью спецификации и планов; финальное ревью включает код, тесты и исходные результаты измерений.

Версии выбраны для воспроизводимости; это не утверждение о последних доступных версиях. Минимальная Java 17 — наше решение, поскольку версия среды BIL24 неизвестна.

## 4. Задание 1: контракт парсера

### 4.1. Публичный API

Сохраняем `test.ParserSeat.parser(String seatName, long id)` с результатом `test.ResultParser`. Сохраняем доступные конструкторы и все getter/setter-методы результата, а также `getFullSector()`, `getFullRow()`, `getFullSeat()`. Имена пакетов и классов оставляем ради прямой замены исходника. Внутренние поля и вспомогательные методы можно переименовывать.

| ID | Требование |
|---|---|
| P1 | Все семь полей и три вычисляемых названия совпадают с оригиналом на одинаковом входе |
| P2 | Отсутствие совпадения возвращает `null`; вход `null` вызывает `NullPointerException` |
| P3 | Сохраняются регулярное выражение, флаги и семантика `find()` |
| P4 | Пробелы, пустые значения, регистр и переводы строк не нормализуются дополнительно |
| P5 | Замены выполняются только в `sectorName`, только для 12 исходных заглавных кириллических букв |
| P6 | `id` переносится без преобразований, включая 0, отрицательные значения и границы `long` |
| P7 | Каждый успешный вызов возвращает независимый изменяемый объект; изменение одного результата не влияет на следующий |
| P8 | Вызовы безопасны при параллельной работе; `Matcher`, буферы и результат принадлежат вызову |

Не обещаем идентичность stack trace, текста исключения или внутренних аллокаций. Случаи нехватки памяти и идентичность экземпляров строк не входят в контракт совместимости. Публичное поведение `ResultParser` при прямом вызове конструкторов и setter-методов сохраняется, включая `null` в полях.

### 4.2. Архитектура оптимизации

1. Одно `private static final Pattern` с исходным выражением.
2. Новый локальный `Matcher` на вызов. Общий `Matcher`, `ThreadLocal` и кэш ответов не нужны.
3. При неудачном `find()` сразу вернуть `null`; объект результата создать после успеха.
4. Ветвление между сектором с названием и без названия сохранить.
5. Однопроходная замена 12 букв: `СЕТНУОРХАВКМ` → `CETHYOPXABKM` соответственно. Для ясности в коде использовать отдельное соответствие каждого символа через `switch`.
6. `StringBuilder` создавать только при первой фактической замене; при отсутствии замен вернуть исходную строку.
7. Сеттеры и методы `getFull*` не менять по смыслу.

Выбрано умеренное изменение внутренней реализации. Минимальный вариант с одним кэшированием `Pattern` проще, но сохраняет многократные проходы по имени сектора. Ручной парсер усложнил бы доказательство совместимости. Если однопроходная замена ухудшает значимый сценарий, результаты анализируются до её принятия.

### 4.3. Эталон и происхождение

Источник: [test_src.zip](https://bil24.pro/test/test_src.zip). Скрипт проверяет SHA-256 полного архива до извлечения. Извлекаются только `src/test/ParserSeat.java` и `src/test/ResultParser.java`; содержимое архива не исполняется как скрипт.

Единственное преобразование эталона — замена ровно одного объявления `package test;` на `package reference;` в каждом файле. Остальное содержимое, включая окончания строк, сохраняется побайтно. Это позволяет вызывать обе реализации напрямую в одной сборке без reflection в измеряемом коде. Обратная замена пакета должна давать исходные байты. Эталон обозначается в отчёте как оригинал с изменённым только именем пакета.

Копия с совпадающей контрольной суммой позволяет повторный запуск без сети. Несовпадение суммы, неверные пути, отсутствие или повторение объявления пакета — ошибка; автоматически принимать новую версию архива запрещено. URL и checksum не являются секретами. Код основной библиотеки не зависит от загрузчика и эталона.

### 4.4. Проверки

| Группа | Конкретное покрытие |
|---|---|
| Фиксированные | Обычный сектор; партер; сектор без имени; все 12 замен вместе и по одной; латиница; строчные буквы; смешанные алфавиты |
| Пробелы и разделители | Два пробела; пустые ряд/место; повторные `Ряд` и `Место`; табуляция; перевод строки до описания и внутри него; CRLF |
| Unicode | Не-ASCII заглавные буквы, supplementary code point, комбинируемый знак, неразрывный пробел |
| Ошибки | Пустая строка; строка без места; `null`; отсутствующий разделитель |
| Результат | Семь полей, три `getFull*`, setter-методы, независимость объектов, границы `long` |
| Сгенерированные | 10 000 входов, `java.util.Random(240915L)`: 3 000 структурированных, 3 000 мутаций, 4 000 произвольных строк длиной до 96 UTF-16 единиц |
| Параллельные | 8 рабочих потоков × 1 000 вызовов, синхронный старт, разные входы и id, сравнение с эталоном и проверка независимости |

Сравнение фиксирует совпадение всех полей и названий либо совпадение типа исключения. На сбое выводятся seed, номер случая, id и вход с экранированием управляющих символов.

Данные ограничены в тестах для управляемого времени выполнения; публичный метод не получает искусственного ограничения длины. Отдельно проверяются корректные строки длиной до 4 096 символов и некорректные до 128 символов. Поведение регулярного выражения на произвольных огромных некорректных строках остаётся ограничением исходного алгоритма; линейная сложность парсера не заявляется.

## 5. Задание 2: контракт шаблонов

Следующие решения заполняют пробелы в условии BIL24 и одобрены при ревью спецификации.

### 5.1. API

Пакет `com.fedrbodr.bil24.template`, класс `CompiledTemplate`:

```java
public static CompiledTemplate compile(String source);
public String render(Map<String, String> replacementMap);
```

Конструктор закрытый. Входные строки неизменяемы. Подготовленный шаблон хранит неизменяемые части; результат каждого `render` — отдельная строка. Для примера загрузки приложение вызывает `Files.readString(path, StandardCharsets.UTF_8)` для каждого из трёх файлов, затем `compile`, и хранит полученные шаблоны весь срок работы.

| ID | Требование |
|---|---|
| T1 | Якорь соответствует `<([A-Za-z_][A-Za-z0-9_]*)>`; ключ в Map указан без угловых скобок; регистр значим |
| T2 | Всё вне совпадений с этой грамматикой сохраняется буквально; совпадение внутри другой конструкции тоже считается якорем |
| T3 | Отсутствующий ключ оставляет исходный якорь; лишние ключи игнорируются |
| T4 | Пустая строка удаляет якорь; `null` для используемого ключа вызывает `IllegalArgumentException` с именем ключа |
| T5 | `null` вместо source или replacementMap вызывает `NullPointerException` |
| T6 | Подстановка однократная и буквальная: `$`, `\`, переводы строк и похожие на якорь значения не интерпретируются повторно |
| T7 | Один шаблон допускает одновременный `render` с разными таблицами; состояние между запросами не переносится |
| T8 | `render` не изменяет таблицу; вызывающий код не изменяет свою таблицу во время вызова |

Значения лишних ключей, включая `null`, не читаются и не валидируются. Копирование всей Map на каждом запросе не требуется при выполнении T8. HTML-экранирование не выполняется: условие описывает обычный текст. Если результат используется как HTML, контекстное экранирование относится к вызывающему приложению.

Пример точной семантики T2: `<<name>>` с `name=Ира` даёт `<Ира>`, поскольку внутренняя последовательность соответствует грамматике. Это не HTML-парсер и не язык шаблонов с вложенными выражениями.

### 5.2. Структура и алгоритм

- `compile`: один проход по совпадениям Pattern; сохранение чередующихся литералов и имён якорей в неизменяемой последовательности частей.
- Часть — закрытый вложенный `record Segment(String text, String key)`; литерал имеет `key == null`, якорь хранит исходный текст и ключ. Такое вложение разрешено стандартом BIL24 для private-классов.
- `render`: локальный `StringBuilder` с начальной вместимостью исходного текста; обход частей, выбор литерала либо значения из Map, добавление в буфер.
- Никаких чтений файлов, регулярных выражений или хранения таблиц клиентов внутри подготовленного шаблона.

Для N символов исходника подготовка имеет линейную стоимость для выбранной простой грамматики; память подготовленного представления — O(N + A), где A — число вхождений якорей. Сам обход и сборка требуют O(A + R) при обычной стоимости lookup Map, где R — длина результата. В выбранной реализации builder заранее резервирует N символов, поэтому полная оценка запроса с выделением буфера — O(N + A + R), временная память — O(N + R). Итоговую строку всё равно нужно сформировать; кэш шаблона не устраняет эту стоимость.

### 5.3. Проверки и объяснение

Проверить пустой шаблон, отсутствие якорей, соседние и повторные якоря, регистр ключей, неверные имена, незакрытые скобки, вложенный вид T2, отсутствие значения, пустое и `null`-значение, лишний ключ, Unicode-текст и буквальные специальные символы. Параллельно выполнить 8 × 100 рендеров с различными данными клиентов и сравнить точные результаты.

В тесте с `@TempDir` создать три разных UTF-8 файла по 512 000 байт, прочитать и подготовить их, проверить длину исходных байтов и точный результат подстановок. Затем удалить файлы и повторить рендер: это подтверждает отсутствие зависимости от диска после подготовки. Размер в 512 000 байт — фиксированная тестовая интерпретация приблизительных 500 КБ из задания.

`docs/template-algorithm.md` должен объяснять загрузку трёх файлов, жизненный цикл шаблона, пример запроса, правила T1–T8, затраты и достаточность решения при нескольких сотнях запросов в день.

## 6. Измерения

Полный протокол и команды — в [методике](../../benchmark-methodology.md).

| ID | Критерий |
|---|---|
| B1 | Парсер сравнивается с зафиксированным оригиналом напрямую на одинаковом корпусе входов |
| B2 | Шаблоны сравниваются с чтением уже загруженной строки и подготовкой при каждом запросе; это наш контрольный вариант, не присланная BIL24 реализация |
| B3 | Время — `ns/op` в одном потоке; пропускная способность — `ops/s` в одном и четырёх потоках; аллокации — `gc.alloc.rate.norm`, `B/op` |
| B4 | Полный запуск: 3 forks, 5 × 1 s прогрева, 5 × 1 s измерений, одинаковые JDK и JVM flags |
| B5 | В измеряемых методах отсутствуют I/O, генерация входов, проверки равенства, reflection и логирование; результаты возвращаются JMH |
| B6 | Сохраняются JSON, полный stdout, команда, commit SHA, checksum эталона, JDK/JVM flags, OS/CPU, дата, параметры и размеры корпусов |
| B7 | Каждый набор параметров публикуется отдельно; произвольные смеси сценариев и единый средний коэффициент не используются |
| B8 | Сначала тесты корректности, затем измерения; короткий smoke-run подтверждает запуск, но не доказывает ускорение |

Цель парсера — уменьшить затраты повторного парсинга. Цель шаблонов — измерить эффект переноса подготовки из запроса в загрузку. Численный коэффициент заранее не назначается. Для заявления об ускорении нужны уменьшение среднего времени и неперекрывающиеся доверительные интервалы JMH в соответствующем сценарии; при пересечении результат помечается как неубедительный.

Любую замеченную регрессию более 5% среднего времени или пропускной способности рассматриваем отдельно: проверяем окружение и доверительные интервалы, при необходимости повторяем только этот сценарий; подтверждённую регрессию исправляем либо явно выносим на ревью. Это критерий разбора, не нестабильный CI-тест.

## 8. Порядок и ревью

Документ и два плана рассматриваются вместе, как запросил владелец. После их одобрения выполняется план парсера, затем план шаблонов. Проверки Superpowers: сначала воспроизводимая проверка, затем изменение, затем проверка результата; небольшие содержательные коммиты. Реализация выполняется в этом самостоятельном репозитории. При разделении работы между агентами задачи выдаются только после чтения применимого плана.

Собеседование, актуальность набора, ставка, принятие решения работодателем и требования его неизвестной Java-среды не являются критериями технической готовности.
